## 第 1 页：背景与目标

### 页面标题

> 电商订单故障排查知识图谱设计

### 内容素材

背景可以这样写：

> 电商系统中订单模块与支付、库存、物流、优惠、售后等模块耦合度高。当订单模块频繁变更或出现故障时，开发人员往往需要同时查看 Git 提交记录、Issue、运行日志和 API 文档，排查成本较高。

目标：

> 构建一个融合业务数据、代码变更、Issue、日志和 API 文档的知识图谱，用于支持故障定位、影响分析和维护决策。

产出：

> 实体列表、关系列表、核心结构图、典型查询、风险点与维护机制。

## 第 3 页：关系设计

根据老师提示，关系要体现“数据源抽取”。

### 需要重点加入这几类关系

老师提示里明确有：

```
Git: commit → 文件修改 → 模块变更
Issue: Bug描述 → 影响模块抽取
日志: LogEvent → 异常类型聚类
API文档: 接口 → 模块映射关系

所以你们的关系列表可以这样设计：

| 来源     | 关系                           |
| -------- | ------------------------------ |
| Git      | Commit —— 修改 —— 代码文件     |
| Git      | 代码文件 —— 属于 —— 系统模块   |
| Git      | Commit —— 影响 —— 系统模块     |
| Git      | 开发人员 —— 提交 —— Commit     |
| Issue    | Issue —— 描述 —— Bug           |
| Issue    | Bug —— 影响 —— 系统模块        |
| Issue    | Bug —— 关联 —— API 接口        |
| Issue    | 开发人员 —— 修复 —— Bug        |
| 日志     | LogEvent —— 属于 —— 系统模块   |
| 日志     | LogEvent —— 聚类为 —— 异常类型 |

| 日志     | TraceId —— 追踪 —— 订单        |

## 第 4 页：核心结构图

这一页建议不要再只画“订单业务流”，而是画成 **四类数据源汇入图谱中心**。

可以用这个结构：

```
                         Git 数据
             Commit → 文件修改 → 模块变更
                         |
                         v
Issue 数据  →  Bug → 影响模块 → 电商故障排查知识图谱 ← API 文档
                         ^                    接口 → 模块
                         |
              LogEvent → 异常类型 → TraceId
                         日志数据
```

然后图谱中心再展开：

```
订单模块
  ├── 关联业务：订单、支付单、库存记录、物流单、售后单
  ├── 关联接口：创建订单、取消订单、支付回调、查询订单
  ├── 关联代码：OrderService、OrderController、OrderMapper
  ├── 关联测试：订单创建测试、支付回调测试、库存扣减测试
  └── 关联故障：支付状态不同步、库存扣减失败、订单超时关闭失败
```

### 推荐 PPT 图形布局

第 4 页可以这样画：

```
         Git Commit / 文件修改
                  ↓
Issue / Bug → 系统模块 ← API 文档 / 接口
                  ↑
        日志 LogEvent / 异常类型
                  ↓
              订单故障排查
```

右侧再放一个例子：

```
订单模块
  ↓
影响：支付模块、库存模块、物流模块
  ↓
相关测试：订单创建测试、支付回调测试、库存扣减测试

## 第 5 页：典型查询问题

这页要根据老师新提示调整。建议你们直接使用老师给的 3 个问题，再补充 2 个。

### 查询清单

| 编号 | 查询问题                           | 图谱路径                                                     | 排查价值           |
| ---- | ---------------------------------- | ------------------------------------------------------------ | ------------------ |
| Q1   | 订单模块变更会影响哪些测试？       | 订单模块 → API 接口 → 测试用例；订单模块 → 代码文件 → Commit | 做回归测试范围选择 |
| Q2   | 最近 30 天 Bug 最多的模块？        | Issue/Bug → 影响模块 → 统计数量                              | 找出高风险模块     |
| Q3   | 谁修复过支付相关 Bug 最多？        | Bug → 影响模块=支付模块 → 修复人员 → 统计数量                | 找到熟悉该问题的人 |
| Q4   | 某个异常日志对应哪个订单和模块？   | LogEvent → TraceId → 订单 → 系统模块                         | 从日志反查业务影响 |
| Q5   | 某次 Commit 可能影响哪些业务链路？ | Commit → 文件 → 模块 → 接口 → 订单/支付/库存                 | 做变更影响分析     |

### 可以放一个具体查询案例

例如：

> 查询：订单模块变更会影响哪些测试？
>  路径：Commit → 修改文件 → 订单模块 → API 接口 → 测试用例
>  结果：订单创建测试、支付回调测试、库存锁定测试、订单取消测试。
>  价值：帮助开发人员确定回归测试范围，减少遗漏。

这和老师提示高度匹配。

## 第 6 页：风险点、维护机制与总结

你新拍的最后一页提到：

> 常见问题 3：缺少维护机制
>  如果不随版本同步更新，图谱一周内就会失效。

所以第 6 页一定要加“维护机制”，不能只写风险。

### 风险与对策表

| 风险点           | 说明                                   | 对策                                   |
| ---------------- | -------------------------------------- | -------------------------------------- |
| 数据源分散       | Git、Issue、日志、API 文档格式不同     | 建立统一抽取规则                       |
| 图谱更新不及时   | 版本更新后关系可能失效                 | 每次发版后自动同步图谱                 |
| 模块映射不准确   | 文件、接口、模块之间可能存在误判       | 人工校验核心模块映射                   |
| Bug 描述不规范   | Issue 内容可能缺少模块、接口、错误类型 | 制定 Issue 模板                        |
| 日志缺少 TraceId | 无法从日志追踪到订单                   | 统一日志规范，必须写入 traceId/orderId |
| 关系过多难维护   | 节点和边越来越复杂                     | 只保留对排障有价值的核心关系           |

### 维护机制要单独写出来

建议写成 4 点：

1. **Git 提交触发更新**
    每次 Commit 后，根据修改文件更新“文件—模块”关系。
2. **Issue 关闭时更新 Bug 关系**
    Bug 修复后，记录修复人员、影响模块和关联 Commit。
3. **日志定期聚类更新异常类型**
    定期分析 LogEvent，将相似异常归类到同一异常类型。
4. **API 文档随版本同步**
    接口新增、删除、修改后，同步更新“接口—模块—测试用例”关系。

### 总结句

可以这样收尾：

> 本方案不是一次性画图，而是构建一个可维护的故障排查知识图谱。通过持续抽取 Git、Issue、日志和 API 文档中的信息，图谱可以随着系统版本变化持续更新，从而支持模块影响分析、Bug 统计、责任人定位和故障排查。
